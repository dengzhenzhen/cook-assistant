# 菜谱、推荐与本地小模型开发方案

> 2026-11-09 实施范围更新：本地模型与微调暂不开发；份量换算改为逐食材可配置非线性规则；今天吃什么采用三种用餐倾向；新增云端食材推荐、可编辑菜单与数据库复用。实际默认值、功能进度及验证见 [实施决策记录](IMPLEMENTATION_DECISIONS.md)。下文模型章节保留为历史规划。

日期：2026-11-08。本文是待实施方案；没有新增运行时功能，也没有做模型性能实测。
部署前提已确认：模型运行在 Python 后端所在电脑或服务器，以 CPU 在后端进程内调用。

## 1. 建议顺序与范围

**主线：结构化与分量换算 → 今天吃什么 → 本地模型接入 → 自有数据微调 → 食材推荐。**

本地推理先安排小规模可行性验证，避免数据和业务都完成后才发现目标 CPU 不合适；正式训练放在数据结构稳定之后。随机推荐、数量计算和排程始终由确定性代码完成。训练数据主来源按用户补充确定为“爬虫采集原始菜谱 → DeepSeek 生成结构化 JSON → 校验清洗 → 小模型 SFT”；人工编辑纠正作为后续补充。

| 阶段 | 交付 | 估算人日 | 完成条件 |
| --- | --- | --- | --- |
| M0 | 数据规范、代表性评测集、CPU 推理验证 | 1–2 | 确定目标硬件、输出契约，至少一个候选可进程内加载和生成 |
| M1 | 菜谱 v2、分量换算、计划快照、编辑器 | 6–9 | 旧数据可迁移，换算和执行使用同一份量 |
| M2 | 今天吃什么、换一批、加入计划 | 3–4 | 候选可解释、可复现，约束和空结果处理正确 |
| M3 | 本地推理适配器、任务路由、CPU 限流 | 3–5 | 不阻塞 API，取消/超时可回收，失败可恢复 |
| M4 | 爬取/清洗、DeepSeek 标注、数据集、LoRA、量化、灰度 | 8–14 | 数据可追溯，自训练模型在保留测试集上达标，有可回退版本 |
| M5 | 食材匹配、缺料清单 | 4–6 | 基于真实菜谱匹配，区分缺失和数量未知 |

合计约 25–40 人日，即单人全职约 5–8 周；是工程排期估计。M4 假设先接入少量结构稳定的菜谱来源；更多站点适配、反爬问题、人工复核、GPU 获取和训练试验可能延长日历时间。M1+M2 是第一批可独立发布的业务版本。爬取/标注可在 M1 输出契约稳定后与 M2 并行推进。

## 3. M1：菜谱结构化与分量换算

### 3.1 数据模型

v2 规范以原始配方为基准，分离可计算数据、原文和推测值。保留现有 tasks/holds 的调度语义。

```json
{
  "schema_version": "2.0",
  "recipe_id": "...",
  "revision": 1,
  "name": "番茄炒蛋",
  "base_servings": 2,
  "category": "main",
  "tags": ["快手"],
  "ingredients": [
    {
      "line_id": "i1",
      "ingredient_id": "tomato",
      "display_name": "番茄",
      "raw_text": "番茄 300 克",
      "quantity": {"kind": "exact", "value": "300", "unit": "g"},
      "role": "main",
      "optional": false,
      "scaling_mode": "linear",
      "origin": "source"
    },
    {
      "line_id": "i2",
      "ingredient_id": "salt",
      "display_name": "盐",
      "raw_text": "盐适量",
      "quantity": {"kind": "to_taste"},
      "role": "seasoning",
      "optional": false,
      "scaling_mode": "manual",
      "origin": "source"
    }
  ]
}
```

此片段只展示新增设计，完整菜谱仍必须包含有效 tasks/holds 等现有必填内容。

- 数量使用带 kind 的联合类型：exact、range（min/max）、to_taste、unknown。缺失数量不等于零。
- 数字以十进制字符串传输，后端用 Decimal，禁止 bool、负数、NaN、无穷值和上下界倒置。
- 支持中文数词、1/2、半、区间和基础单位别名；无法可靠解析则保留 raw_text，标为 unknown 待确认。
- 基础单位分为质量 g、体积 ml、计数个等；中国大陆市斤明确为 500g。杯、勺、把、袋不能静默假设统一规格。
- g↔ml 必须有对应食材密度；个↔g 必须有用户确认的单个重量。映射缺失时不转换。
- ingredient_id 是稳定的食材字典键。首批维护常见食材和别名，如西红柿/番茄；保留豆腐/豆腐干、生抽/老抽等区别。
- 人数缺失时可保留现有默认基准，但必须标为 estimated、待用户确认；不能把原代码默认 2 当作原文事实。
- 新增 `step.ingredient_refs` 等结构化引用逐步替代步骤中的硬编码用量；旧 notes 不用正则直接改数字。
- 预留类别、口味和已确认限制标签，为随机推荐复用；未知标签不能伪装成已确认。

### 3.2 换算规则

基本公式：`目标用量 = 基准用量 × 目标份数 / 基准份数`。

| 情况 | 默认行为 |
| --- | --- |
| 300g、20ml 等明确数量 | 按比例缩放，最终展示时才舍入 |
| 2–3g | 两个端点分别缩放 |
| 鸡蛋 3 个换到 1.5 倍 | 显示理论值 4.5 个，另外给人工确认的操作建议，不能后台改成 5 个 |
| 盐适量、少许、未知 | 保留语义，不补数字 |
| 油、水、调味品具有特殊规则 | 第一版可给比例参考，并标“需按锅具/口味调整”；仅对已确认配方应用专用规则 |
| 锅底油、腌料等固定用量 | 只有配方明确指定 fixed 时才保持不变 |
| 炒制、焖煮时间与火力 | 不按人数线性倍增；大份量提示重新确认容量和时间 |

每次都从基准配方计算。2→4→3 人应等于直接 2→3 人，避免累积舍入。显示精度和实际计算精度分开。

第一版只承诺“食材用量换算”。现有厨房模型没有锅具容量，因此不能承诺大份量排程仍适用；超过建议缩放范围时要求用户确认。自动分锅、批次 DAG 与时长曲线留待后续扩展。

### 3.3 接口和页面

新增接口建议使用 `/api/v2`，继续维护现有 v1 边界：

- `POST /api/v2/recipes/{id}/scale-preview`：传目标份数与原配方修订号；返回食材、原文、计算依据及需确认项，不覆盖菜谱。
- `POST /api/v2/plans/from-recipes`：以 `items:[{recipe_id, revision, target_servings}]` 代替只有 recipe_ids 的选择；仍传 kitchen_id、目标开饭时间。
- 计划保存独立 scaled recipe snapshot、基准修订号与缩放规则版本；开始烹饪后配方变化不能改变正在执行的会话。
- 前端展示“原配方 2 人份 → 本次 3 人份”，允许按菜覆盖；购买清单的取整量与实际配方量分开。
- 多菜汇总只合并相同食材、兼容单位与同一形态；“鸡胸肉”和“鸡肉”不直接合并；适量项单独列出。

### 3.4 兼容和迁移

1. 新增 v2 数据模型和 v1↔v2 适配，不直接把 Literal['1.0'] 改为 2.0 后读取旧文档。
2. 备份原 document，使用幂等迁移脚本，记录数量解析成功/未知/需确认清单。新增表和列通过 Alembic 管理。
3. 旧 v1 读接口投影为原字段；旧写入必须保留无法表达的 v2 信息，无法安全合并时拒绝并提示升级。
4. 新增菜谱修订号和乐观并发控制；旧客户端不带修订号的写入不能覆盖已有 v2 扩展数据。
5. 升级 uni-app 缓存、离线 outbox 的序列化和冲突处理。旧待同步编辑先迁移；无法无损处理的保留双方草稿。
6. 导入模型输出经过统一转换后再保存。只确认菜谱不等于允许拿用户原始资料训练；纠正样本的采集另设明确选择。

### 3.5 验收

覆盖精确值、区间、半个、分数、适量、单位不兼容与缺失份数；验证不累积舍入、原菜谱不被覆盖、越权访问被拒绝。旧菜谱、旧缓存、离线待同步数据和执行中会话均有回归用例。数量正确率按人工标注集统计，不能用 JSON 合法率代替。

## 4. M2：今天吃什么

### 4.1 首版交互

在计划页和菜谱页提供入口：默认返回 3 道候选，支持“换一批”“保留这道”“加入今晚计划”。加入后进入现有份量确认和厨房排程流程。首版候选来自用户有权限访问、已确认的菜谱库；库为空时提供导入入口。

如果需要直接生成一桌菜，可作为后续增强：按主食/荤菜/素菜/汤组合，允许替换单道。首版先把单菜候选与加入计划做完整。

### 4.2 算法与限制

先过滤，再加权无放回抽样：

- 硬限制：用户明确排除的食材、已确认的饮食约束、不可用的必需设备；限制永不自动放宽。
- 软偏好：收藏、口味、菜类、近期做过和本轮看过。可将近期做过降权，不能直接假设收藏越多越应该重复。
- 烹饪历史依据实际会话完成事件；“推荐过”“加入计划”“完成烹饪”分别记录。
- 单次结果不重复；保留菜品不被换掉；菜谱不足时返回实际数量和原因。
- 默认降低最近 7 天完成菜品的权重；排除、时间范围和偏好参数均可配置。
- 需要随机 seed 用于测试复现和问题追踪；候选先按稳定 ID 排序，版本化权重规则。

建议接口 `POST /api/v2/recommendations/random`，传 count、filters、keep_ids、exclude_ids；返回 recipe_id、匹配理由、放宽了哪些软偏好、seed 和算法版本。查询和事件都按 user_id 隔离。

时间条件在推荐阶段只能用 DAG 最长路径等估算粗筛；不能将所有 task 时长相加当作出餐时间。用户选择后才运行 OR-Tools，返回厨房约束下的可行时间；近似值不承诺为硬时间保证。

### 4.3 验收

给定 seed 可复现；批次不重复；keep/exclude 正确；硬限制不被突破；无候选有明确说明；选中菜谱能按目标份量进入现有计划。用固定候选集验证权重变化方向，避免以脆弱的单次随机结果作断言。

## 5. M0/M3：CPU 进程内推理

### 5.1 模型选择与任务边界

已核实存在 Qwen3-0.6B 与 Qwen3.5-2B；如果要同代对比，Qwen3 对应的相邻档位是 1.7B。不同代架构、模板、运行库支持不同，不能只替换模型路径。Qwen3-0.6B 支持关闭 thinking；本任务使用非思考模式。[官方 0.6B 模型卡](https://huggingface.co/Qwen/Qwen3-0.6B)、[官方 2B 模型卡](https://huggingface.co/Qwen/Qwen3.5-2B)

先对 0.6B 建立延迟和准确率基线，再对比 1.7B 或准确的 2B 候选；若资源预算允许，优先从已经通过兼容性验证且语义指标更好的候选开始微调。具体版本需锁定模型 revision、转换工具、llama.cpp 和 Python binding，2B 路线先验证架构支持、聊天模板和量化导出。

首个可验证任务为：**食材行解析、数量语义识别、名称规范化候选，以及有原文依据的菜谱基础字段提取。** 用户计划的“菜名 → 完整菜谱 JSON”作为第二项明确训练目标，使用独立任务标识和评测集；详见 6.1。两类任务不能混用“仅菜名时必须拒绝”的系统提示。

- 完整 DAG、holds、厨师注意力建模已有较复杂约束，继续使用现有链路或人工编辑；不得将基础抽取通过理解为完整排程建模通过。
- 随机抽签、Decimal 换算、食材匹配和 CP-SAT 求解由业务代码执行。
- 抽取模式输入只有菜名时返回“资料不足/需要搜索”。菜名生成模式可以给出待确认配方，但不能宣称来自某条原文；小模型不自带搜索，查找真实来源由独立检索层完成。
- 图片首版沿用现有云端通道；全本地图片需要增加本地 OCR → 文本解析，另做准确率和 CPU 预算。选了支持视觉的 2B 也不能直接沿用文本端到端性能估计。

### 5.2 推荐调用链

```text
uni-app → FastAPI 导入任务 → 持久化 ImportJob
                            ↓
                     有界任务准入 / 能力路由
                            ↓
               专用线程 + 单个 LocalRecipeParser
                            ↓
                 llama-cpp-python → llama.cpp
                            ↓
                         GGUF / CPU
                            ↓
               结构校验 + 语义校验 → 待确认草稿
```

Python binding 提供本地 C API 调用与 JSON Schema 输出限制，因此可以在同一个后端进程内调用，不必启动推理 HTTP 服务。格式限制不保证食材、数量和操作语义正确，仍须单独校验。[llama-cpp-python 文档](https://llama-cpp-python.readthedocs.io/en/latest/)

建议新增：

```text
backend/service/ai/contracts.py       # ParsedIngredients / ParseResult
backend/service/ai/providers.py       # 按任务选择 provider
backend/service/ai/local_parser.py    # 模型实例、模板、约束生成
backend/service/ai/validation.py      # 通用输出校验和转换
backend/service/cpu_budget.py         # 排程和推理共享的准入策略
```

配置至少包含 provider、模型路径/摘要、上下文上限、输出 token 上限、线程数、队列容量、执行超时和 allow_cloud_fallback。默认不因本地解析失败自动上传输入；显式开启云端回退后才使用现有 DeepSeek。

### 5.3 并发、取消与资源

- 单后端进程、单模型实例、单专用执行线程，第一版推理并发为 1。数据库会话不跨线程共享，传递普通不可变任务数据。
- 使用后端 lifespan 管理实例；模型未就绪时返回能力不可用，菜谱 CRUD/随机推荐仍可工作。关闭时先停止接单，再协作取消并等待实际计算结束，最后释放模型。
- 复用 ImportJob 持久状态，增加 cancelled/timeout 等状态与 provider/model/schema/prompt 版本。内存队列有界，数据库中待处理任务也限制准入，满载返回明确繁忙状态。
- 等待超时和执行超时分开。asyncio.wait_for 或取消 Future 不会终止原生推理；以 token 检查点和可验证的原生 abort 回调配合 deadline，底层真正结束后再释放实例锁。
- 任务结果按执行标识和当前状态条件写入，防止取消后的迟到结果把 cancelled/timeout 改回 completed；启动时明确恢复 pending，并将中断的 running 标为可见失败或按策略重试。
- 验证 prompt prefill 阶段能否中止。纯进程内无法承诺在 native hang/segfault 时只结束模型；异常无法恢复时需要服务重启。若业务要求强制杀死单次推理且主服务继续运行，就必须重新讨论进程隔离，与当前进程内要求有取舍。
- 统一 plans/generate、plans/recalculate 和 plans/from-recipes 的 CPU 准入。现有 from-recipes 未使用 app.py 的排程 semaphore。
- OR-Tools 当前 num_search_workers=1；本地推理也限制 CPU 线程，先用小线程数做压测，给执行接口保留余量。低核数机器可将推理与求解串行，并让执行重排优先，避免推理任务把重排饿死。
- `generate_plan(...time_limit_seconds=3)` 是各次 solve 的上限，多个优化目标可能连续求解，不能当作整个 HTTP 请求严格 3 秒。
- 首版部署只开一个 Uvicorn worker；多进程会各自加载模型、各自维护锁和队列，内存/并发都不再是全局 1。当前任务领取和恢复也不足以保证多进程不重复执行。
- 锁定二进制依赖和 CPU 指令集构建；防止生产 CPU 不支持构建机指令。进程内调用节省的是服务调用开销，主要延迟仍取决于 prefill、生成长度与内存带宽。

### 5.4 接入现有导入的关键修改

不能只新增 local_parser.py：需要一并解除 api/ai.py 的 DeepSeek key 前置检查、provider 无关的作业摘要、云端配额与本地容量分离、AIUsage 增加 provider/model/duration/status。摘要纳入输入、任务类型、模型/模板/Schema 版本；旧缓存不能误用新输出。

当前成功任务会清空输入，只留下 parser_version。训练样本需要另建受控存储，记录明确同意保留的原文、初次输出、人工最终版本、变更原因及版本；可删除、可导出，避免把普通运行日志当训练集。

### 5.5 性能验证和发布门槛

在实际目标 CPU 上记录型号、核心数、RAM、指令集和后端负载。用短/中/长输入同时测试冷启动、热启动、P50/P95 总时延、prefill、生成速度、RSS、失败率，以及推理期间的排程和执行接口延迟。

第一轮测试从 2k 上下文和 256–512 输出 token 的食材提取开始，随后测试 4k；这是试验配置，不是已验证最优值。短输出抽取作为主用例，长全文菜谱走已有能力或明确提示超限。

约 4 bit 的纯权重下限为 0.6B≈0.3GB、2B≈1GB；实际 GGUF 和 RSS 还有混合精度、元数据、KV/状态缓存与工作区。PoC 可分别预留约 1–2GB、2–4GB 作为起始预算，最终以实测为准。

建议初始产品目标：基准食材抽取热启动 P95 ≤ 5 秒、整条异步导入 ≤ 20 秒；无法满足就缩小任务或换候选。它们是待验证目标，没有硬件信息前不承诺 tokens/s。混合负载下 CRUD/执行交互 P95 增幅目标 ≤ 20%，执行重排不被队列长期阻塞。

## 6. M4：自己微调小模型

### 6.1 爬虫 + DeepSeek 教师标注

用户补充的主流程可行：通过菜名组织采集，爬取真实菜谱，DeepSeek 产出结构化标签，再训练 Qwen 小模型。这是使用教师生成标签做 SFT 的路线；只用最终文本标签，不要求获取教师 logits 或思考过程。

当前 `search_recipe` 已有“菜名 → 搜索资料”能力，`ImportWorker` 再调用 DeepSeek 结构化；可复用格式和验证代码。批量数据生产应是独立离线流水线，不直接用线上账号任务队列跑全量采集。当前搜索把多个结果拼接，批量标注先采用“一份来源正文 → 一个标签”，避免同名菜不同版本被混成一道配方。

```text
菜名清单 / 分类入口
    → 采集、正文提取、来源与内容指纹
    → 精确及近似去重、质量筛选、分组切分
    → DeepSeek 按固定版本提示词输出 JSON
    → Schema / DAG / 食材数量与步骤语义检查
    → 人工抽检与问题回流
    → 构造不同任务的输入/输出样本
    → LoRA SFT → GGUF 量化 → CPU 评测
```

#### 6.1.1 保留完整的数据生产记录

每条至少保存 `sample_id`、source_url、source_site、采集时间、raw_text、content_hash、菜名、原始配方版本、teacher_model、prompt_version、schema_version、teacher_raw_output、validated_json、validation_errors、review_status、split_group。老师输出和人工修订分别保留。

爬虫以站点 adapter 拆分，支持限速、失败重试、断点和增量更新；优先采集明确可使用、结构稳定的来源，保留来源和使用条件。抓取本身不推定获得内容的训练或再分发许可。正文清洗移除导航、广告、评论与相邻菜谱；不绕过登录或访问限制。

建议离线新增 `scripts/dataset/` 与独立数据目录：按 raw / labeled / reviewed / splits / exports 分层，原文与大文件不进入 Git。具体命令在实现时确定。

#### 6.1.2 输入/输出配对决定小模型学什么

| 任务 | 输入 | 输出 | 评测重点 |
| --- | --- | --- | --- |
| A：菜谱结构化 | 固定抽取指令 + 原始菜谱正文 | 有原文依据的 JSON | 食材/数量忠实、步骤不遗漏、未知值保留 |
| B：菜名生成 | 固定生成指令 + 菜名 + 已知版本/偏好 | 对应的完整 JSON 草稿 | 配方合理、一致、限制满足、可校验 |
| C：检索后结构化 | 菜名 + 检索到的真实原文 | 对应 JSON | 检索命中率、来源忠实度与结构准确率 |

只保存 JSON 再做无输入语言建模，不能保证学会 A 或 B。SFT 样本需要与线上同形的输入和目标输出；训练框架支持 messages 或 prompt/completion 数据格式。[TRL SFT 数据格式](https://huggingface.co/docs/trl/sft_trainer)

同一批正文和标签可以派生 A/B 数据，但任务指令必须区分。任务 B 的训练输入不能偷偷附上仅训练时可见的正文；推理只有菜名，评测也必须只有菜名。人数明确时可带基准人数；分量变化继续由确定性代码计算。

同名菜有多个版本时，先选定默认版本，或在输入标明“家常版/少油版”等原文真实存在的条件。不要把不同完整答案当成字段完全一致的标准答案；生成评测允许合理的多解。菜名和食材数量/做法冲突的样本先排除。

模型目标标签使用固定字段顺序和稳定局部步骤 ID；UUID、owner、抓取 URL、运行时版本、用户收藏等由程序生成，不让模型逐 token 学习。源文本中的缺失时长保留未知；若完整调度标签确实需要教师推估，必须写入 estimated_fields，单独评测，不能当作原文事实。

#### 6.1.3 教师标签不是可靠真值

每条先做 JSON/Pydantic、数值和单位、任务引用、依赖环与 holds 合法性检查；再比对原文食材、用量、动作覆盖、顺序和教师新增内容。JSON 合法不等于菜谱正确，DAG 无环不等于烹饪顺序合理。跨步骤持锅、并行关系与注意力类型列为高风险复核项。

失败样本最多做有限次纠正，仍失败进入隔离集；不循环调用教师直到碰巧通过。人工分层抽检复杂菜谱、未知单位和所有推估字段，建立独立人工金标集；同一个教师的二次评审只作辅助，不作为唯一验收。

首批处理约 500–1,000 份原始菜谱，人工校验其中约 300–500 份，用于确认提示词、Schema、通过率和小模型学习效果；再按失败类别扩展到数千份去重后的有效菜谱。若主攻菜名生成，需扩展菜名/菜系/做法覆盖，不能靠重复采集少数热门菜增加样本量；不承诺某个固定条数就能泛化。

先去重，再按原菜谱/近似内容和来源成组切分（例如 80/10/10），同源改写、OCR 与合成变体不得跨集合。任务 A 另留站点/文风外测试集；任务 B 分别报告见过菜名的新问法与完全未见菜名测试，后者按菜名/变体家族隔离。提示词调整只看验证集，最终测试集保持冻结。

成本通过首批统计：每条输入/输出 token、一次通过率、纠正次数、实际有效样本数与人工复核时间；按届时实际计费估算扩量预算，不预设固定成本。

#### 6.1.4 上线路由建议

保留用户现有“输入菜名”的交互，可先走：标准菜名/别名查询本地已校验 JSON → 有命中直接返回 → 未命中按配置检索后由小模型结构化或回退现有 DeepSeek。对于已经入库的菜，直接取 JSON 更快且可追溯，无需让小模型重新生成。

若目标是完全离线处理未知菜名，则专门训练任务 B，并接受它输出的是生成草稿；它不能保证准确记住所有配方，也不能证明来自爬取来源。先比较 0.6B 和更大候选在 B 上的实际质量，再决定能否替代现有功能。完整 Recipe JSON 较长，需按真实输出长度重新测 CPU 延迟，不能沿用食材抽取的短输出结果。

### 6.2 训练与导出

推荐先使用现有指令模型做监督微调 SFT+LoRA。LLaMA-Factory 当前文档列出 Qwen3 和 Qwen3.5、非思考模板，并支持 LoRA/QLoRA；须锁定实际可运行版本，不直接照搬旧 Qwen2.5 示例。[LLaMA-Factory 官方仓库](https://github.com/hiyouga/LlamaFactory)

试验起点：rank 8/16，alpha 16/32，学习率 5e-5–1e-4，1–3 epoch；依据验证集早停。训练和推理的模板、字段、非思考模式要一致。先跑通 50 条数据的训练→合并→转换→CPU 回归闭环，再做完整训练。

训练建议在独立 GPU 环境完成；CPU-only 是线上推理要求，不能据此估计 CPU 训练可用。GPU 型号、显存和时长待小批实测；显存受序列长度、batch、优化器和架构影响。

产物链路：原始数据/标注版本 → 训练集 → LoRA adapter → 在高精度基座上合并 → 导出 HF → 转 GGUF → 对比 Q8_0 与 Q4_K_M → CPU 评测 → 灰度。Qwen 官方有 llama.cpp 转换与量化指南；各候选仍需逐一确认转换支持。[Qwen 量化指南](https://qwen.readthedocs.io/en/latest/quantization/llama.cpp.html)

### 6.3 如何决定是否上线

固定比较：规则解析器、未微调模型、微调高精度模型、微调量化模型；都使用同一个保留测试集和输出约束。不能把更严的 JSON grammar 带来的改进误判为微调能力提升。

建议第一轮门槛（作为目标而非已有成绩）：

- 合法输出经校验 ≥99%；食材识别 F1 ≥95%；数量与单位联合准确率 ≥95%。分别报告含歧义输入和明确输入，不能只报告总体平均。
- 在“资料不足”集能正确保留未知，不能通过填入更多字段掩盖幻觉；测试集中虚构食材/明确用量事件必须单独计数与审查。
- 与未微调基线比较，语义指标有稳定改善，且复杂/罕见输入不过度退化；用样本数和置信区间解释差异。
- 量化后主要语义指标下降目标 ≤1 个百分点，并满足 CPU 时延与内存预算。
- 用户侧依然先得到待确认草稿；只有基础抽取达标时，不开放未经验证的自动 DAG 生成。
- 任务 B 不以某一份源菜谱的逐字段完全相同作为唯一准确率：另评配方内部一致、菜名对应、偏好满足、步骤完整和 DAG/holds 的语义正确性，报告 seen-name 与 unseen-name 结果。

模型版本记录权重 SHA、基座 revision、数据/训练配置、模板/Schema、量化方式、运行库版本与完整评测结果。先离线回放，再小流量灰度；保留上一版本和 cloud/manual 模式，故障通过配置回退。

## 7. M5：根据食材推荐（低优先级）

第一版只做“输入已有食材 → 匹配我的菜谱 → 显示缺什么”，不做完整冰箱库存、保质期和自动扣库存。

复用 M1 食材字典、单位和 M2 过滤机制，新增由原菜谱生成的 ingredient 检索投影；投影随菜谱保存事务同步更新，权限仍按菜谱所有者限制。SQLite 即可起步，不先上向量库。

匹配按角色加权：主料高、辅料中、调味料低；先排除不符合硬限制的候选，再按覆盖率、缺失主料数、需购买项目数和偏好排序。

```text
覆盖率 = 已有必需食材的权重之和 / 菜谱必需食材的权重之和
```

optional 食材不作为必需缺失。调味料可由用户一次确认“家里常备”，不能默认人人都有。不允许“鸡肉”无条件替代“鸡胸肉”，缺少依据的替换建议另行确认。

只输入名称时，显示“食材种类匹配，用量未确认”；输入数量且单位可转换时，按目标份量判断是否足够，返回缺口。不兼容单位和未知数量标为“无法判断”，不能展示成“全部齐全”。

建议 `POST /api/v2/recommendations/by-ingredients`，返回匹配食材、缺失食材、数量不足/未知项和解释。首版推荐理由由规则模板生成，无需调用语言模型。

验收覆盖别名、多单位、未知数量、缺少主料、optional、未确认常备调料、跨用户隔离和按人数变化后的缺口。

## 8. 实施与验证清单

建议拆成可独立评审的交付：

1. 输出规范、食材字典与小型人工评测集；候选模型 CPU PoC 报告。
2. Recipe v2、数量解析、Decimal 缩放、迁移和兼容适配。
3. uni-app 结构化编辑、分量预览、计划快照与离线兼容。
4. 随机推荐 API、事件记录、页面与计划接续。
5. 供应方解耦、统一排程准入、模型生命周期与有界队列。
6. 离线爬取/DeepSeek 标注、抽检与样本导出；LoRA 配置、量化与回归报告；灰度开关。
7. 食材检索投影、匹配和缺料页面。

每个交付运行相关后端用例；前端变化运行 Node 测试，并构建 H5 和微信小程序。完成 M1 后做一次“旧菜谱→迁移→换算→计划→执行→离线恢复”的端到端回归；M3 做取消和混合 CPU 负载测试；M4 把模型评测单列，不能以业务单测代替。

现有可复用命令：仓库根目录 `.venv/bin/python -m pytest -q`；`frontend/uniapp` 内 `npm test`、`npm run build:h5`、`npm run build:mp-weixin`。模型评测、迁移和压测入口在对应阶段补齐并文档化。

本轮仅制定方案，未运行上述功能测试、模型训练或 CPU 基准。主代理整合验收了只读勘察（explorer：gpt-6-luna / low）与进程内推理设计（architect：gpt-6-astra / high）；实际功能和模型指标须在实施阶段验证。
