# 本轮功能实施与默认决策

日期：2026-11-09。用户已授权持续开发，不进行询问；每完成一个功能点，验证后提交并 push 一次。已有本地模型与微调方案保留为历史规划，本轮不实施。

## 未询问、直接采用的默认值

| 原本需要确认的问题 | 本轮默认决策与原因 |
| --- | --- |
| “几个菜”指食材还是菜数？ | 食材单独输入，菜数使用 1–6 的条件，推荐列表仍允许增减。 |
| 哪个客户端实现？ | 当前正式 uni-app（H5、微信小程序、App 共用源码）；不扩展旧 Flutter / HTML 原型。 |
| 数据升级是否另建 v2？ | 兼容现有 v1 JSON，保留 quantity/unit 原文，添加结构化 amount 与逐食材 scaling。规范化离线基准，避免新增默认字段引起伪冲突。 |
| 默认份数与允许范围？ | 保留原配方份数，本餐可逐菜设 1–20 人份；缺省不改变原份数。 |
| 不同材料如何非线性变化？ | 支持线性、指数、固定＋变量、固定、手动、分段。调味默认指数 0.8；常见炒菜油参考 30% 固定＋70% 随量变化；水/高汤默认人工确认。都是可改的产品参考，不是通用烹饪规律。 |
| 默认规则不适用于某道菜怎么办？ | 菜谱编辑器可逐项覆盖；烘焙、腌制等比例敏感配方应设明确规则，不能盲用调味默认值。 |
| 未知数量、勺杯、半个和范围怎么办？ | 明确数值/分数/范围可计算；不猜密度或容器规格，不把适量转克数；计数小数保留理论值，由用户分取。 |
| 大小份会否改变时间和火力？ | 不自动改变。超过基准 0.5–2 倍额外提示核对容量、调味与分锅；步骤原文数字不盲替换，本餐食材清单单独保存。 |
| 分段曲线超出节点范围？ | 不自动外推，保留原用量并提示人工调整；曲线必须有 (1,1) 基准且单调。 |
| 今天吃什么模式如何划分？ | 10分钟快手菜：1道/10分钟/低工作量；普通一顿：2道/30分钟/中工作量；吃顿好的：3道/60分钟/高工作量。份数默认2，可修改。时间先作为推荐倾向，最终获得步骤后才能核验排程。 |
| 云端 LLM 选择？ | 复用已有 DeepSeek 配置、服务器密钥与配额，不增加本地模型。 |
| 菜单何时补全菜谱？ | 先只生成菜名列表，用户可编辑增减；确认后按当前账号数据库匹配，只有缺失项才导入，不预先生成所有菜谱。 |
| AI 菜谱是否直接开始排程？ | 保留现有编辑确认流程。未确认的草稿不能进入烹饪计划。 |
| 菜单或导入部分失败？ | 保留草稿与成功项，重试失败项；不静默重复生成已存在的菜谱。 |

## 功能1：结构化与逐食材分量换算

已实现结构化数量解析、逐食材曲线、换算预览、计划/执行快照及编辑表单；原配方不因本餐换算被覆盖。旧文本编辑会重新计算 amount，避免沿用过时数值。

验证：后端换算/菜谱/认证与离线回归 40 项通过；前端 Node 测试通过；H5、微信小程序构建通过。Chromium 移动视口实际完成登录、结构化编辑、选菜及 2→4 人份预览，验证主料 300→600g、油量 10→17ml，未出现页面运行时错误。API 在浏览器验证中使用模拟数据，未调用付费服务。截图见 `structured-ingredients-preview.png`、`portion-scaling-preview.png`。

环境说明：沙箱内 aiosqlite 的线程唤醒被阻塞，使用内存数据库复现；同一检查在沙箱外正常，因此后端集成测试在沙箱外运行，仍只使用临时测试数据库。没有为此修改应用数据库逻辑。
