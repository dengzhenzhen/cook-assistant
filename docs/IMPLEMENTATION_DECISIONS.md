# 本轮功能实施与默认决策

日期：2026-11-09。用户已授权持续开发，不进行询问；每完成一个功能点，验证后提交并 push 一次。已有本地模型与微调方案保留为历史规划，本轮不实施。

## 未询问、直接采用的默认值

| 原本需要确认的问题 | 本轮默认决策与原因 |
| --- | --- |
| “几个菜”指食材还是菜数？ | 食材单独输入，菜数使用 1–6 的条件，推荐列表仍允许增减。 |
| 哪个客户端实现？ | 当前正式 uni-app（H5、微信小程序、App 共用源码）；不扩展旧 Flutter / HTML 原型。 |
| 数据升级是否另建 v2？ | 兼容现有 v1 JSON，保留 quantity/unit 原文，添加结构化 amount 与逐食材 scaling。规范化离线基准，避免新增默认字段引起伪冲突。 |
| 默认份数与允许范围？ | 保留原配方份数，本餐可逐菜设 1–20 人份；缺省不改变原份数。 |
| 不同材料如何非线性变化？ | 支持线性、指数、固定＋变量、固定、手动、分段。调味默认指数 0.8；常见炒菜油参考 30% 固定＋70% 随量变化；水/高汤默认人工确认。都是可改的产品参考，不是通用烹饪规律。 |
| 默认规则不适用于某道菜怎么办？ | 菜谱编辑器可逐项覆盖；烘焙、腌制等比例敏感配方应设明确规则，不能盲用调味默认值。 |
| 未知数量、勺杯、半个和范围怎么办？ | 明确数值/分数/范围可计算；不猜密度或容器规格，不把适量转克数；计数小数保留理论值，由用户分取。 |
| 大小份会否改变时间和火力？ | 不自动改变。超过基准 0.5–2 倍额外提示核对容量、调味与分锅；步骤原文数字不盲替换，本餐食材清单单独保存。 |
| 分段曲线超出节点范围？ | 不自动外推，保留原用量并提示人工调整；曲线必须有 (1,1) 基准且单调。 |
| 今天吃什么模式如何划分？ | 10分钟快手菜：1道/10分钟/低工作量；普通一顿：2道/30分钟/中工作量；吃顿好的：3道/60分钟/高工作量。份数默认2，可修改。时间先作为推荐倾向，最终获得步骤后才能核验排程。 |
| 云端 LLM 选择？ | 复用已有 DeepSeek 配置、服务器密钥与配额，不增加本地模型。 |
| 菜单何时补全菜谱？ | 先只生成菜名列表，用户可编辑增减；确认后按当前账号数据库匹配，只有缺失项才导入，不预先生成所有菜谱。 |
| AI 菜谱是否直接开始排程？ | 保留现有编辑确认流程。未确认的草稿不能进入烹饪计划。 |
| 菜单或导入部分失败？ | 保留草稿与成功项，重试失败项；不静默重复生成已存在的菜谱。 |
| “工作量倾向”如何核验？ | 获得完整菜谱后，将需操作与间歇看管时长累计为人分钟；低/中/高参考上限为10/30/90人分钟。超限明确显示，可返回菜单调整，不把它伪称为精确劳动量。 |
| “10分钟”是每道菜还是整餐？ | 菜单推荐的时间目标按整餐理解；完成步骤解析后使用当前厨房整餐排程核对，计入锅具冲突与被动烹饪，不计等待未来开饭目标前的空闲。 |
| 食材是硬限制还是优先使用？ | 默认优先使用已有食材，允许补少量辅料；模型结果是建议，完整配方生成后用户核对。未输入数量时不承诺现有库存用量足够。 |
| 多次点击与并发确认会重复导入吗？ | 同一后端进程内序列化缓存检查、配额预留和入队，规范化菜名；已有 pending/completed 导入直接复用。保持现有单进程部署；多进程全局任务领取仍需额外协调。 |
| 老编辑器不带新的食材规则怎么办？ | 对名称与单位唯一匹配的食材保留原规则；显式传入 auto 可以重置。重复同名食材不猜测行对应关系。 |

## 功能1：结构化与逐食材分量换算

已实现结构化数量解析、逐食材曲线、换算预览、计划/执行快照及编辑表单；原配方不因本餐换算被覆盖。旧文本编辑会重新计算 amount，避免沿用过时数值。

验证：后端换算/菜谱/认证与离线回归 40 项通过；前端 Node 测试通过；H5、微信小程序构建通过。Chromium 移动视口实际完成登录、结构化编辑、选菜及 2→4 人份预览，验证主料 300→600g、油量 10→17ml，未出现页面运行时错误。API 在浏览器验证中使用模拟数据，未调用付费服务。截图见 `structured-ingredients-preview.png`、`portion-scaling-preview.png`。

环境说明：沙箱内 aiosqlite 的线程唤醒被阻塞，使用内存数据库复现；同一检查在沙箱外正常，因此后端集成测试在沙箱外运行，仍只使用临时测试数据库。没有为此修改应用数据库逻辑。

## 功能2：三种用餐模式

已实现“10分钟快手菜 / 普通一顿 / 吃顿好的”，支持人数、菜数、时间和工作量自定义；调用已有云端 DeepSeek 只生成菜名菜单。结果可改名、增减和换一批，改名后清除旧菜谱链接与旧估时；草稿按账号保存，失败不丢失。唯一匹配的已确认库中菜谱可直接加入计划，同名歧义不擅自选择。

验证：新增后端推荐测试 10 项通过（覆盖全部模式默认值、模拟 DeepSeek 协议、配额、错误响应、同名歧义和账号隔离）；既有后端测试在集成检查中通过。Node 测试、H5 与微信小程序构建通过。Chromium 已完成快手与丰盛模式切换、请求与可编辑菜单显示，截图见 `meal-menu-quick-preview.png`、`meal-menu-feast-preview.png`。所有云端请求在验证中均被模拟，没有产生真实 API 费用。

## 功能3：根据食材推荐与菜谱复用

已实现已有食材与人数/菜数/时间/工作量一起询问云端 LLM；返回菜名草稿后可增减改名。确认菜单才按账号隔离的数据库匹配，唯一已确认菜谱复用，同名多个展示人份/食材摘要供选择，未确认菜谱进入审核，缺失项复用原有持久导入任务。原料优先使用而非库存精确保证；不将菜名相似度当作相同配方。

导入成功仍需在编辑器审核保存，返回菜单后重新匹配库中菜谱。缺少配置或配额只使对应行失败，保留其他成功项；重试已有任务不重复扣费。编辑/删除菜名、切账号后迟到结果不会覆盖当前菜单。生成/解析时锁定相关菜单编辑，防止条件变化与返回结果不一致。

新增完整步骤后的厨房排程核对。两道各6分钟的菜在单锅串行时显示整餐12分钟，明确超过10分钟目标；份数改变时提醒原时长仍是基准估算。操作与看管时长累计为人分钟，不用 LLM 的时间猜测替代排程结果。

最终验证：`.venv/bin/python -m pytest -q` 共83项全部通过；前端 `npm test` 通过，`build:h5`、`build:mp-weixin`、`build:app` 全部通过。App 验证为资源构建，不等同于签名安装包或实机验证。

新增完整集成用例真实经过临时数据库、持久导入worker、审核保存和本地 OR-Tools，只替换外部 LLM/搜索响应；验证编辑后的菜名才导入、库中菜谱不重复生成、已完成导入再匹配不增加配额。另有并发请求用例证明单进程同名导入只入队一次。

Chromium 对最终构建跑通“食材输入 → 菜单改名 → 库内复用/局部失败 → 仅重试失败行 → 草稿审核保存 → 加入计划 → 整餐超时提示”，没有页面运行时错误。截图：`ingredient-menu-partial-preview.png`、`ingredient-menu-review-preview.png`、`menu-schedule-assessment-preview.png`。真实云端响应质量与微信/App 实机体验尚未验证。
