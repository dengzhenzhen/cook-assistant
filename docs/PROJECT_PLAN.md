# AI 智能烹饪助手项目规划

## 1. 产品目标与边界

帮助家庭用户把菜谱转换为可编辑的任务 DAG，并结合厨具数量、厨师人数和开饭时间安排多菜烹饪。核心闭环是：导入菜谱 → 确认修正 → 选择菜品 → 配置厨房 → 生成计划 → 执行与重排。

正式产品沿用既定方案：Flutter 移动端、FastAPI 服务、PostgreSQL、Redis/Celery 和 OR-Tools。HTML 原型用于确认界面及交互，不等同于已完成 Flutter 客户端。AI 解析与确定性调度分离；额度耗尽不应阻止手动编辑、排程和执行。

MVP 不包含视频解析、摄像头烹饪识别、智能家居控制、营养分析、购物、社区或多人实时协作。

## 2. 当前基线

| 模块 | 已有能力 | 尚缺能力 |
| --- | --- | --- |
| 调度引擎 | Pydantic 请求校验、DAG 检测、资源累计约束、跨任务持有、分层优化、执行事实约束 | 具体厨具分配、间歇关注时间窗、会话事件管理 |
| 运行入口 | JSON 命令行、FastAPI 调度、持久化菜谱/厨房、DeepSeek 导入与任务查询 | 正式鉴权、会话幂等与并发控制 |
| 测试 | 30 项后端测试、5 项 Flutter 测试、7 项 HTML 执行逻辑测试，浏览器核心流程检查 | 正式离线恢复、客户端提醒与多设备验证 |
| 服务层 | SQLAlchemy/Alembic、持久化菜谱/厨房/导入/用量、原子配额、开发账号 | 正式登录、Celery/Redis、会话持久化 |

## 3. 代码与职责

```text
backend/
  cook_scheduler/  # 纯调度库，不依赖 HTTP、数据库或 AI
  service/         # API、业务编排、持久化及 AI 适配
  tests/           # 调度及服务回归测试
frontend/
  mobile/          # Flutter 正式工程（Android/iOS/Web）
  index.html       # 保留 HTML 交互原型
examples/          # 可重复运行的调度请求
docs/              # 项目规划、接口约定与产品决策
```

服务层把 Recipe、KitchenProfile 和 Execution 转为调度 Request；调度库返回 Plan。持久化菜谱模板与会话任务快照，编辑菜谱不得改变已开始的会话。

## 4. 分阶段交付

以下工作量为初步估算，需在人员、AI 服务和部署条件确定后排期。

| 阶段 | 主要工作 | 验收标准 | 初步工作量 |
| --- | --- | --- | --- |
| M0 规划与交互验证 | HTML 原型、页面流转、关键决策记录 | 用户可走通选菜到执行的流程，并确认界面及交互 | 2–4 人日 |
| M1 数据与基础服务 | 用户、菜谱模板、厨房配置、迁移、手动创建编辑 | 重启服务后数据保留；默认厨房可编辑且资源允许为 0 | 5–8 人日 |
| M2 菜谱导入 | 文本与图片、异步任务、版本化 Schema、用户修正、配额 | 上传菜谱得到可编辑结果；失败能重试；AI 推断有标记 | 7–12 人日 |
| M3 调度集成 | 菜谱到 Request 转换、计划 API、时间转换、缺资源反馈 | 三菜一饭无资源冲突，无法满足目标时有明确反馈 | 5–8 人日 |
| M4 烹饪执行 | 会话快照、状态机、幂等、计时、动态重排、离线记录 | 完成/延误后重排不改历史事实；断网后继续已下载计划 | 8–12 人日 |
| M5 平台能力与试用 | URL 导入降级、分享入口、系统提醒、日志、成本统计 | iOS/Android 实机后台提醒与真实厨房试用通过 | 7–12 人日 |

先完成手动菜谱到调度的闭环，可独立推进 AI 导入。Flutter 系统分享、通知和离线能力需要实机验证，HTML 演示不能代替验收。

## 5. 页面与状态

底部主导航遵循「菜谱 / 做饭 / 我的」，厨房配置属于「我的」。计划与执行页面放在「做饭」路径下。

| 页面 | 核心操作 | 必须表达的状态 |
| --- | --- | --- |
| 菜谱列表 | 导入、收藏、选入本餐 | 无菜谱、未选择、已选择 |
| 导入与确认 | 文本/图片/URL、校对任务与时长、保存 | 解析中、失败、待确认、AI 估算 |
| 厨房配置 | 数量增减、厨师数、保存 | 资源为 0、未保存、保存成功 |
| 计划设置 | 选菜、开饭时间、生成 | 计算中、缺资源、目标不可达 |
| 计划预览 | 时间线、主动/被动任务、资源占用 | 可行解、超时可行解、无解 |
| 烹饪执行 | 开始任务、确认完成、查看计时器、重排 | 待开始、进行中、等待确认、完成 |

## 6. 数据与接口推进

- Recipe 采用版本化结构，任务依赖由程序校验；任务编辑触发 DAG 与资源持有区间的重新校验。
- 时间在服务边界使用带时区的日期时间，进入引擎前统一转换为会话相对秒数。
- 首批服务接口：菜谱 CRUD、默认厨房读写、`POST /api/v1/plans/generate`。
- 会话阶段补充 start/complete、pause/resume、recalculate，并用事件 ID、版本号和事务避免重复写入及并发覆盖。
- 用户已确认：仅自动设备任务可在预计结束后进入自动确认倒计时，默认 60 秒、可设 5–600 秒；手动与明火任务仍需点击确认。倒计时期间保留资源，完成后按最新计划衔接。运行中的明火不能因 App 暂停而被视为停止。
- URL 获取设置大小、超时、重定向与网络地址限制；无法读取的平台提供截图/文本降级入口。
- AI 输入输出均视为待校验数据；密钥保存在服务端，导入前原子预留额度，结果记录用量和成本。

## 7. 验证与发布门槛

保留现有调度回归用例，逐步增加三菜资源冲突、持续持锅、目标时间不可达、运行任务超时、历史一致性和极端输入验证。服务层验证鉴权隔离、幂等与数据恢复；移动端验证后台计时、权限拒绝和断网重连。

上线前至少完成：一套三菜一饭的真实厨房演练、API 失败恢复、AI 额度耗尽后的手动流程、数据备份恢复，以及 iOS/Android 实机通知验证。

## 8. 已确认决策与待定事项

用户已确认本次采用：**手机 App 界面 + 完整核心流程 + 真实 Python 调度引擎**。其他尚未实现的能力以明确标注的演示数据呈现。本地原型使用「开饭」作为工作名称，暖白、橄榄绿和陶土橙作为可调整的视觉草案。

本阶段已实现：四道示例菜谱、文字/图片/URL 演示导入、手动创建与编辑、收藏与选菜、厨房配置、目标日期时间、真实时间线与资源占用、开始/完成/延长后的真实重排、演示快进及单浏览器进度恢复。运行方式见 `frontend/README.md`。

HTML 原型的导入仍展示固定示例。新增 Flutter 客户端接入了真实 DeepSeek 文本/图片导入和数据库持久化，密钥仅在服务端。执行页同时显示手动操作及自动设备计时，步骤支持详细操作备注，完成确认后自动衔接。仅自动设备可倒计时自动确认，这是用户已确认的产品选择。HTML 暂停冻结演示时钟；Flutter 正式执行暂停只停止安排新步骤，物理运行和提醒继续。M0 可用于交互评审；M3 的原型适配已完成，但不能视作完整生产服务交付。

以下事项仍由用户决定，后续开发前确认：

- 正式名称及视觉方向是否保留。
- AI 使用预算、首发平台和部署环境。登录已按本轮需求采用邮箱密码与轮换令牌。AI 供应商已由用户指定 DeepSeek，已验证可用模型为 deepseek-flash。
- 暂停时如何处理明火、人员与不可中断任务；允许跳过哪些步骤。
- 用户编辑跨步骤资源持有关系的交互方式。

未确认事项不作为已定需求实施。
